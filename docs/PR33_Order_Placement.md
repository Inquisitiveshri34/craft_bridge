## Section 3 – Objective

This PR implements the order placement flow — the complete path from a buyer reviewing their cart to a confirmed order document in Firestore. `FirestoreService.createOrder()` and `updateOrderStatus()` are implemented, `OrderProvider` gains a `createOrder()` method, and `CartScreen` is fully implemented as a stub cart (no `CartProvider` yet — that is PR42) that allows buyers to review a single product from `ProductDetailScreen` and place a real order. After this PR, buyers can place orders that appear in `ArtisanOrdersScreen` in real time.

**`createOrder()` method:**

```dart
Future<bool> createOrder({
  required String buyerId,
  required String buyerName,
  required ProductModel product,
  required int quantity,
}) async {
  _isLoading = true;
  _errorMessage = null;
  notifyListeners();
  try {
    final String orderId = FirebaseFirestore.instance
        .collection(AppConstants.ordersCollection)
        .doc()
        .id;
    final OrderModel order = OrderModel(
      id: orderId,
      buyerId: buyerId,
      buyerName: buyerName,
      artisanId: product.artisanId,
      artisanName: product.artisanName,
      productId: product.id,
      productTitle: product.title,
      productImageUrl: product.imageUrl,
      quantity: quantity,
      totalPrice: product.price * quantity,
      status: AppConstants.statusPending,
      createdAt: Timestamp.now(),
    );
    await _firestoreService.createOrder(order);
    _isLoading = false;
    notifyListeners();
    return true;
  } catch (e) {
    _errorMessage = 'Failed to place order: $e';
    _isLoading = false;
    notifyListeners();
    return false;
  }
}
```

**Implementation notes:**

- The order ID is generated via `FirebaseFirestore.instance.collection(AppConstants.ordersCollection).doc().id` — same pattern as `ProductProvider.addProduct()`.
- `totalPrice: product.price * quantity` — computed at order creation time. This snapshot price is stored in the order document, so price changes to the product do not retroactively affect placed orders.
- `status: AppConstants.statusPending` — all new orders start as pending.
- `productImageUrl: product.imageUrl` — snapshot of the image URL at time of order. If the artisan later changes the product image, the order card still shows the original image.

**`_handlePlaceOrder()` method:**

```dart
Future<void> _handlePlaceOrder() async {
  final authProvider = context.read<AuthProvider>();
  final orderProvider = context.read<OrderProvider>();
  final String? buyerId = authProvider.currentUser?.uid;
  final String? buyerName = authProvider.currentUser?.displayName;
  if (buyerId == null || buyerName == null) {
    ScaffoldMessenger.of(context).showSnackBar(
      const SnackBar(
          content: Text('Error: user not authenticated.')),
    );
    return;
  }
  setState(() => _isPlacingOrder = true);
  final bool success = await orderProvider.createOrder(
    buyerId: buyerId,
    buyerName: buyerName,
    product: widget.product,
    quantity: _quantity,
  );
  setState(() => _isPlacingOrder = false);
  if (!mounted) return;
  if (success) {
    ScaffoldMessenger.of(context).showSnackBar(
      const SnackBar(content: Text('Order placed successfully!')),
    );
    Navigator.of(context).popUntil((route) => route.isFirst);
  } else {
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(
        content: Text(
          orderProvider.errorMessage ?? 'Failed to place order.',
        ),
      ),
    );
  }
}
```

**Note on `Navigator.of(context).popUntil((route) => route.isFirst)`:** After a successful order, the buyer is returned to the root of the navigation stack (`BuyerHomeScreen`). `popUntil` with `route.isFirst` pops `CartScreen` and `ProductDetailScreen` in one operation, landing on `BuyerHomeScreen`.

## Section 10 – Video Explanation Talking Points

This is intentional — e-commerce platforms always snapshot the price at purchase time. If the artisan later raises the price of a product, existing orders retain the original price. A simple `Navigator.pop()` would only pop `CartScreen`, leaving `ProductDetailScreen` visible. `popUntil` with `route.isFirst` collapses the stack in a single operation, which is the correct UX for a completed purchase flow."

4. **`CartItemTile` in `CartScreen`:** "`CartScreen` uses the `CartItemTile` widget from PR22 for the item display. The tile shows the product image, title, artisan name, quantity stepper, line total, and remove button. `onRemove` calls `Navigator.pop(context)` — since this is a single-item cart, removing the item means cancelling the checkout, which is the back navigation."

5. **`_buildOrderSummary` bottom-pinned layout:** "The order summary is bottom-pinned using `Column` with `Expanded(ListView)` above and `_buildOrderSummary()` below. This means the artisan can change an order from 'pending' to 'confirmed' without affecting `buyerId`, `totalPrice`, or any other field. PR37 wires this method to the status bottom sheet in `ArtisanOrdersScreen`."

8. **Order ID generation consistency:** "`OrderProvider.createOrder()` generates the order ID via `FirebaseFirestore.instance.collection('orders').doc().id` — the same pattern used in `ProductProvider.addProduct()`. The ID is embedded in the `OrderModel` and used as the Firestore document path. This ensures `order.id` and the document key are always identical, which is required for `updateOrderStatus(orderId, ...)` to find the correct document."

9. **Real-time cross-role verification:** "After a buyer places an order, the artisan's `ArtisanOrdersScreen` updates in real time — no refresh needed. This works because `OrderProvider.listenToArtisanOrders()` uses a Firestore stream that fires on every document change in the `orders` collection filtered by `artisanId`. The new order document triggers a stream emission, `_artisanOrders` updates, `Consumer<OrderProvider>` rebuilds, and the new `OrderCard` appears."
